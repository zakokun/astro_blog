最近做了一个面向用户的个人仓储服务。它有用户端，也有管理后台，后端提供 API，数据落在 MySQL，文件放在对象存储里，还会对接短信、实名认证、门锁和支付相关服务。本地调试的时候，很多事情都很顺，页面能打开，接口能通，数据库也能连上。真准备把服务发到线上时，问题开始变多：哪些文件该进 Git，哪些配置不能进仓库，静态资源放哪里，用户上传的身份证照片怎么传，数据库能不能暴露公网，后端发布失败怎么回滚，证书过期谁提醒，短信服务被刷了怎么办。这些事单独看都不复杂，放到一个真实服务里，就变成了一套上线前必须处理的工程问题。

## 代码仓库先收拾干净

很多项目最早出问题的地方是 Git。用上 Git 以后，很容易把所有东西都往仓库里放。本地调试会产生日志、缓存、临时文件、前端构建出来的 `dist`、后端编译出来的二进制文件，这些都不该进仓库。二进制文件尤其没有必要提交，它又大，又不方便看 diff，换一台机器或者换一个系统架构还可能不能用。仓库里应该保存源码、脚本、文档和必要的配置模板，构建产物交给发布流程处理。`.gitignore` 看起来是小文件，实际很重要，它决定了仓库会不会在几个月以后变成一个什么都塞进去的杂物箱。

配置文件更麻烦。很多人在本地调接口的时候，会把生产环境的数据库密码、短信服务密钥、对象存储 AccessKey、第三方平台 Secret 直接写进配置文件里。调通以后顺手一提交，这个 Key 就进了 Git。只要 Key 进过 Git 历史，就不能再当成安全的 Key。把文件删掉再提交一次没有用，历史记录里还在，远端仓库、CI 日志、别人的 clone、fork 都可能留下痕迹。正确处理方式是立刻禁用或者轮换泄露的 Key，再清理 Git 历史。后面再用 `.env`、`config.toml`、云平台 Secret 或 CI/CD Secret 管理真实配置，仓库里最多提交一份 `config.example.toml`，告诉自己和协作者需要哪些字段。

这个问题在个人仓储服务里尤其明显。它可能同时用到 MySQL、短信、对象存储、实名认证 OCR、临时上传凭证、门锁平台和支付配置。任何一个 Key 泄露，都不只是“配置错了”这么简单。短信接口可能被刷出费用，对象存储可能被恶意上传，实名认证资料可能被访问，门锁相关接口甚至会影响线下设备。AI 可以很快帮你把调用代码写出来，但这些 Key 放在哪里、权限给多大、泄露以后怎么处理，最终还是要由项目负责人决定。

## 前端上线不是把 dist 扔到服务器上

前端构建出来以后，最省事的做法是把 `dist` 放到云服务器目录里，让 Nginx 直接读出来。访问量很小的时候这样可以用，长期看不太合适。普通云服务器的出口带宽通常不大，JS、CSS、图片、字体这些静态资源会吃掉大量带宽。用户一多，静态资源回源会拖慢服务器，后端 API 也可能跟着受影响。更稳妥的做法是把静态资源放到对象存储，再接 CDN。HTML 缓存短一点，带 hash 的 JS 和 CSS 可以缓存久一点。发布新版本时，要知道哪些资源需要刷新 CDN，哪些资源靠文件名 hash 自然更新。代码已经发布了，用户浏览器或者 CDN 还在拿旧文件，这类问题排查起来很烦。

用户上传文件也要单独设计。最省事的写法是让浏览器把文件传给业务服务器，再由业务服务器上传到对象存储。小流量时看不出问题，文件一大、并发一高，服务器带宽很快会被打满。更合适的链路是前端直传对象存储。业务服务器只负责校验登录态，然后下发一个短时间有效的临时凭证，前端拿着这个凭证上传文件。这个凭证的权限要收紧，有效期几分钟，只能写指定 bucket，最好只能写当前用户自己的目录。这样即使凭证泄露，影响范围也比较有限。上传完成后，服务端仍然要记录文件归属、大小、类型和业务状态，不能完全相信前端传回来的地址。

这里也有一个很容易犯的错误：把对象存储的长期 AccessKey 写进前端代码。前端代码构建以后会变成静态资源，用户可以下载、格式化、搜索，里面没有真正意义上的秘密。任何出现在前端包里的 Key，都要按已经公开处理。前端能拿到的只应该是临时凭证，而且这个凭证要有有效期和权限边界。

## 后端发布要能退回去

后端发布要留退路。脚本语言可以按目录保留不同版本，Go 这类编译型语言可以保留每次构建出来的二进制。新版本发布时，不要直接把老版本覆盖到找不回来。线上一旦出问题，最重要的是快速恢复服务，而不是现场重新构建一次。发布脚本至少要做几件事：构建新版本，上传到服务器，备份当前版本，替换运行版本，重启服务，检查健康状态。如果健康检查失败，就切回旧版本。这个流程写起来不花哨，但真出问题时会救命。

数据库迁移要更谨慎。生产环境不要随便把自动迁移绑在服务启动里。加字段通常还好，删字段、改字段类型、批量迁移历史数据都要提前备份，最好有单独的迁移命令和维护窗口。代码发布和数据库变更还要考虑兼容性：旧代码能不能读新表，新代码能不能读旧数据，某个字段为空时会不会直接报错。很多线上事故不是新代码完全不能跑，而是新旧版本、缓存、数据库结构在发布过程中短暂不一致，某个接口刚好踩到了这个状态。

## 数据库要有边界和备份

个人项目和小团队能用托管数据库就先用托管数据库。自己维护 MySQL 不只是把服务装起来，还要处理备份、升级、磁盘、监控、权限和故障恢复。托管数据库至少把很多基础运维问题先兜住了。真正要注意的是访问边界。生产数据库不要开放公网访问，只允许业务服务器的内网地址或固定 IP 访问。云平台一般都会提供安全组、白名单、RAM 权限控制，这些要认真配置。不要为了本地调试方便，就把生产数据库开到公网，再用一个弱密码连上去。

备份也要打开。我用的云平台在一定容量内提供免费备份，这种能力应该用起来。还要定期确认备份真的能恢复。服务挂了可以重启，代码坏了可以回滚，机器没了可以重建，生产数据没了就很难补回来。面向用户的仓储服务里会有订单、租约、付款记录、用户身份信息、仓位状态，这些数据比代码更重要。代码仓库丢了还有可能重写，生产数据丢了，很多业务关系就断了。

## 服务器只开放必要入口

云服务器上也要收口。安全组里只开业务需要的端口，Web 服务开 80 和 443，SSH 如果必须开 22，最好限制来源 IP，关闭密码登录，只允许密钥登录。有条件可以用堡垒机。数据库、Redis、管理面板这类端口不要暴露到公网。后端服务可以只监听本机端口，比如 `127.0.0.1:8080`，由 Nginx 反向代理出去。外部用户访问的是 HTTPS 域名，不直接碰后端进程。这样就算后端框架、调试端口或内部接口有问题，也不会直接暴露在公网扫描下面。

HTTPS 也不要拖到最后再处理。前端如果走 CDN，就在 CDN 上配置证书；后端 API 一般在 Nginx 上配置证书，再反向代理到本机服务。Let's Encrypt 可以免费签证书，但证书有有效期，要配置自动续期，至少也要有到期提醒。HTTP 可以保留用于跳转到 HTTPS，不建议让用户长期用 HTTP 访问。Cookie、CORS、前端 API 地址也要跟着 HTTPS 一起改，线上还留着 localhost 或 http 地址，会出现登录态丢失、跨域失败、页面请求失败这类问题。

在中国大陆部署网站还要考虑备案。域名接入大陆服务器或者大陆 CDN，通常绕不开 ICP 备案。备案号也要显示在网站底部。这个事情技术含量不高，但真上线时经常卡人。很多服务本地跑得很好，域名、证书、备案、CDN 这些流程没处理完，用户还是访问不了。

## 云服务权限要拆开

服务稍微真实一点，就会开始接各种云服务：短信、对象存储、实名认证 OCR、CDN、日志、支付、AI API。不要用一个主账号 AccessKey 管所有东西，也不要给 RAM 用户开管理员权限。每一种服务最好单独建 RAM 用户，只给它需要的权限。短信服务的 Key 只允许发短信，对象存储的 Key 只允许操作指定 bucket 或指定目录，OCR 的 Key 只允许调用 OCR。这样某个服务出问题时，影响范围更小，轮换 Key 也更清楚。

按量计费的服务还要设置用量告警和账单告警。短信接口被刷、OCR 被刷、OSS 被恶意上传、CDN 被刷流量，最后都会反映到账单上。有些问题不一定会让服务立刻挂掉，但会让成本失控。上线服务的时候，安全和成本经常连在一起。权限给得越大，接口越开放，费用被刷起来的空间也越大。

## 上线以后要看得见问题

服务上线以后，不能只靠用户反馈知道它坏了。至少要有基础日志、错误记录、健康检查和告警。日志里不能打印密码、token、验证码、身份证信息、AccessKey 这类敏感内容。后台系统还应该记录关键操作，比如谁改了订单，谁关闭了租约，谁确认了付款，谁查看了敏感信息。出了问题以后，如果没有日志和审计，只能靠猜。

监控不用一开始就做得很复杂，新项目的访问量通常也不需要一上来就盯着各种性能指标。但也正因为是新项目，机器配置往往很低，磁盘也很小，最容易被忽略的是日志。访问日志、错误日志、应用日志如果一直写下去，几天或者几周后就可能把磁盘打满。日志要做 rotate，保留最近一段时间就够了，老日志该压缩就压缩，该清理就清理。除此之外，服务是否存活、接口错误是否变多、磁盘是否快满、数据库是否连不上、证书是否快过期、账单是否异常上涨，这些事情要有人知道。很多小项目上线初期没有专门运维，开发者自己就是最后一道防线。看得见问题，才有机会在它变成事故前处理掉。

## 写在最后

现在写出一个能跑的项目越来越容易。页面、接口、表结构、CRUD、登录、上传，AI 都能帮你很快生成出来。真正拉开差距的地方，会越来越偏向系统判断：配置怎么放，权限怎么拆，数据库怎么保护，静态资源怎么发，服务怎么回滚，费用怎么控制，出了问题怎么定位。会写代码仍然重要，但只会写代码已经不够了。一个面向用户的服务只要开始处理登录、订单、文件、数据库和第三方云服务，就要对数据、安全、成本和恢复能力负责。架构师思维听起来很大，落到实际项目里，往往就是这些上线前必须想清楚的小事。
