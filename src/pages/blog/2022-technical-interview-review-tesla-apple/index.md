2022 年，我参加过特斯拉和苹果国内岗位的技术面试。几年以后再回头看，其中一些题目并不算特别难，真正影响发挥的往往是紧张、思路混乱，以及不知道应该怎样向面试官展示自己的思考过程。

这篇文章不是面试题库，只记录几道我印象比较深的题，以及当时犯过的错误。时间已经过去比较久，具体流程也可能发生变化，内容以个人回忆为准。

## 特斯拉：并发程序应该怎样结束

特斯拉面试的第一道题是经典算法题：如何判断一个链表是否有环。

这道题我以前刷过，很快就想到了快慢指针。慢指针每次走一步，快指针每次走两步。如果链表中存在环，两个指针最终会相遇；如果快指针走到了链表末尾，则说明链表没有环。

当时我明明做过这道题，却还是故意装作思考了一会儿。现在看来没有什么必要。遇到见过的题，可以直接告诉面试官，然后把解法、原理、边界条件和复杂度解释清楚。是否第一次见到题目并不重要，真正需要展示的是自己有没有理解。

第二道题是 Go 并发编程题。题目大意是：从 `1～100` 中取数，启动 10 个生产者和 10 个消费者，保证每个数字只被处理一次。

我在程序最后的退出逻辑上出了问题。

生产和消费的主体逻辑并不复杂，真正让我混乱的是：生产者使用的 channel 和消费者使用的 channel 应该先关闭哪一个？`WaitGroup` 应该先等待生产者，还是先等待消费者？

我没有理清这些 goroutine 之间的依赖关系，只是在关闭 channel 和调用 `Wait()` 的顺序上反复尝试，最后导致程序死锁。面试官当时马上还有会议，希望我尽快结束。我心里也知道，这次大概率没戏了。

现在重新回答，顺序应该是：

1. 将 `1～100` 写入任务 channel，发送完成后关闭它。
2. 生产者从任务 channel 中读取数据，并将处理结果写入结果 channel。
3. 等待所有生产者退出，然后关闭结果 channel。
4. 消费者读取完结果 channel 中剩余的数据后自然退出。
5. 最后等待所有消费者结束。

关键不是背诵这个顺序，而是先弄清楚谁还可能继续向 channel 写入数据。只有能够确定“以后不会再有数据写入”的一方，才应该关闭这个 channel。

这道题让我意识到，会启动 goroutine 并不代表真正理解并发。并发程序不只需要考虑任务如何执行，还要考虑所有 goroutine 最后怎样安全退出。

面试最后，对方又用英语问了几个关于公司看法的问题。最终我没有通过这次面试。

## 苹果：先讲架构，再进入技术细节

相比之下，苹果的题目更接地气。题目没有那么偏算法，更多是在讨论技术方案、架构设计和技术选型。

第二轮有一道让我印象很深的系统设计题：

> 假设不同星球上都部署了客户端，地球上的服务端需要接收这些客户端发送的数据。怎样保证数据传输的正确性和稳定性？怎样避免数据的时间顺序错乱？数据量很大时又应该如何优化？

“不同星球”放大了分布式系统中常见的问题：距离远、延迟高、网络不稳定，不同客户端的时间也未必一致。

我当时犯的错误，是过早钻进了具体的技术细节。因为想向面试官展示自己的技术能力，我一直在讨论局部实现，却没有先从全局解释架构，也没有先确认面试官对数据顺序、延迟和可靠性的具体要求。我能明显感觉到，面试官对这个回答并不满意。

后来考取 AWS 架构师认证以后，我才逐渐理解这类题应该怎样回答。面试官未必期待某个固定方案，更想看到的是候选人如何确认需求、拆解问题，并解释不同方案的成本。

拿到题目以后，可以先确认几个条件：

- 客户端使用什么协议上传数据？
- 上传的数据量和频率是多少？
- 系统可以接受多大的延迟？
- 顺序要求是单个客户端内部有序，还是所有客户端全局有序？
- 服务端返回成功时，数据必须已经进入数据库，还是只要完成可靠接收即可？

确认这些条件以后，再从基础设施和应用设计两个层面展开。

### 改善客户端到服务端的网络

如果客户端分布在很远的地方，就不应该让它们全部直接连接同一个中心服务。

以 AWS 为例，可以通过 [Global Accelerator](https://docs.aws.amazon.com/global-accelerator/latest/dg/introduction-how-it-works.html) 一类的服务，让客户端从距离自己较近的边缘节点进入云服务商的全球网络，再由这条相对稳定的线路连接后端服务。CloudFront 也可以转发 `POST`、`PUT` 等请求，但它更偏向内容分发；如果重点是改善动态请求和上传链路，Global Accelerator 更符合这个场景。

服务端还可以采用多区域部署，让客户端把数据写入距离自己较近的区域。存储层可以考虑 [DynamoDB Global Tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GlobalTables.html) 之类的多区域数据库，让不同区域都能提供本地读写。

这些基础设施可以改善连接质量和区域容灾，但不能代替应用自身的可靠性设计。

### 保证数据可追踪、可重试

每条上报数据都应该携带唯一 ID，并记录设备 ID、节点 ID 和单调递增的序列号。

唯一 ID 可以用于去重，设备或节点 ID 用于确定来源，序列号则可以帮助服务端判断数据是否丢失、重复或者乱序。客户端还需要保存尚未成功上传的数据，在网络中断后继续重试。

由于重试可能造成重复发送，服务端的写入操作也要具备幂等性。不能简单地把“收到两次”变成“写入两次”。

时间顺序也不能完全依赖客户端时间戳，因为不同客户端的时钟可能存在偏差。如果只要求单个客户端内部有序，可以按照“设备 ID + 序列号”排序。

如果要求所有客户端之间严格全局有序，问题就会复杂很多。系统需要引入统一排序或者共识机制，同时承担更高的延迟和实现成本。因此，回答前必须先确认面试官所说的“顺序”到底是哪一种顺序。

### 先可靠接收，再异步处理

客户端不一定要等待数据真正写入最终数据库。

服务端可以先把数据写入可靠的消息队列或持久化日志，完成这一步后就向客户端返回成功。后端消费者再从队列中批量读取数据，异步写入数据库。写入失败时进行重试，超过重试次数的数据进入死信队列，等待后续排查和处理。

这里的前提是“可靠接收”。如果数据只是进入服务进程的内存，服务端就立即返回成功，那么进程崩溃后，已经确认的数据仍然可能丢失。

死信队列也不等于“保证一定写入成功”。它只是把最终处理失败的数据保存下来，避免这些失败被悄悄忽略。

### 做好冷热数据分层

多个节点不断上报数据，在线数据库的体量会越来越大。没有必要让所有历史数据一直留在昂贵的在线数据库中。

常用的处理方式叫作冷热数据分层，也可以称为数据生命周期管理或数据归档。

在线数据库保留近期、经常查询的热数据。较旧的数据可以定期导出到 S3，按照日期、设备或者数据来源进行分区。访问频率进一步下降以后，再通过[生命周期规则](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html)转移到成本更低的归档存储。

这样既能控制在线数据库的体量和成本，也能保留历史数据供分析、审计或者故障排查使用。

## 后来再看这两次面试

特斯拉的并发题让我发现，自己当时只考虑了程序如何运行，没有考虑程序如何结束。

苹果的系统设计题则暴露了另一个问题：我太急于证明自己知道多少技术细节，没有先向面试官展示自己如何理解和拆解整个问题。

技术面试并不只是检查答案是否正确。尤其是并发和系统设计题，面试官还会观察候选人怎样确认需求、怎样组织思路，以及遇到问题后能不能找到清晰的分析路径。

这些能力，我是在面试失败以后才慢慢补上的。
